# 讲什么、按什么顺序讲

听众记不住画面，记得住一条主线。先定主线，再画图。

## report：向上汇报 / 项目复盘

对应 `templates/report.html`，完整示例 `examples/ai-translation`。

主线是“情境 → 冲突 → 问题 → 答案”的变体：

| 段落 | 页数 | 这一段要让听众知道什么 | 画面 |
| --- | --- | --- | --- |
| 开场 | 1 | 结论：改了什么、省了多少 | split 封面，右边是全景图，左边 2–3 个关键数字 |
| 现在的流程 | 3–6 | 现在是怎么做的，一步一步长出来 | 每页多出 1–2 个节点，同一张图逐步完整 |
| 改哪一段 | 1–2 | 只动哪一段、为什么是这一段 | 其余部分 `dim`，瓶颈 `hot()` + 红色标签 |
| 怎么改 | 2–3 | 新流程长什么样、怎么兜底 | 删掉旧节点、加入新节点，同 id 的平滑过渡 |
| 效果 | 2–4 | 成本、时间、质量，各一页 | 独立的柱状图场景 + `card.bars` |
| 总结 | 1 | 三项结果 + 下一步 | 回到新流程全景，打开指标条 |

要点：

- **先讲现状再讲方案**。老板不一定熟悉一线流程，直接讲方案他判断不了改得对不对。
- **说清没改什么**。“开发、产品、发布都不动”能打消“影响面多大”的顾虑。
- **效果一页只讲一个指标**。成本、时间、质量混在一页，哪个都记不住。
- **主动讲短板**。比如“30 条里有 8 条同事更好”，比只报平均分更可信。
- 结尾给下一步，让听众知道要他做什么。

## system：系统讲解 / 新人入职

对应 `templates/system.html`，完整示例 `examples/order-flow`。

| 段落 | 页数 | 画面 |
| --- | --- | --- |
| 开场 | 1 | split 封面，右边是整张系统图 |
| 全景 | 1 页 + 3–5 拍 | 一页里用 beats 逐块推近：入口 → 核心 → 存储 → 异步，最后拉回全景 |
| 主流程 | 1–2 | 一条请求从头走到尾，`flows` 串起整条路线 |
| 故障场景 | 2–3 | 每页一个故障：`down()`、`fail` 数据包、红色标签 |
| 高峰 / 扩容 | 0–1 | `crowd` 人数变多、`hot()`、标签写峰值 |
| 总结 | 1 | 记住哪几件事；去哪看代码、找谁 |

要点：

- **一张图从头用到尾**。系统讲解最怕每页换一张图，新同事会以为是不同系统。
- 全景页用 beats，不要拆成 5 页。拆页会丢掉“它在整体里哪个位置”的感觉。
- 故障场景比正常流程更值得讲：新同事真正需要的是“出事了看哪里”。

## 技术分享 / 概念讲解

没有专门模板，从 `system` 改：

- 每页推进一个概念，画面跟着概念长出来（例如：一台服务器 → 加负载均衡 → 加缓存 → 加 CDN）。
- 每页 `changes` 写清这一页加了什么、去掉了什么。
- 数字推算放信息卡：`'1000万 × 20 = 2亿 次/天'`、`'= 约 2,300 次/秒'`。

## 页数和时长

- 大约每分钟 1 页；一页带 3 拍以上时算 2 页。
- 10 分钟的汇报：12–18 页。超过 20 页就该砍。
- 一页的口播超过 4 句，就拆页或拆拍。
